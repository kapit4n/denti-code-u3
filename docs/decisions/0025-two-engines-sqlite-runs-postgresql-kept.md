# ADR 0025 — Two engines: SQLite runs the product, PostgreSQL is kept

- **Status:** Accepted
- **Date:** 2026-10-06
- **Deciders:** Principal Architect, Product Owner
- **Affects:** database strategy, `apps/api` persistence layer, `database/`, test strategy, tooling
- **Partially supersedes:** [ADR 0003](./0003-postgresql-only-for-now.md)

## Context

ADR 0003 chose PostgreSQL as the only database, and AGENTS.md rule 16 recorded
"No SQLite yet". The reason for that choice was that two persistence systems
before the product model is understood is how a project drowns in sync bugs.

What has actually hurt in daily use is different: **the Docker dependency.**
Every machine that wants to run this project needs a container runtime, a
compose file, a port, a volume and a migration step before the first request
goes out. `pnpm run db:up` is the first command a new contributor runs and the
first one that can fail for reasons that have nothing to do with this codebase.

The product owner asked for SQLite. Two clarifying questions narrowed it:

1. _Why?_ — "kill the Docker dependency". Not offline mode, not a file to ship,
   not portability. The container, not PostgreSQL, is the pain.
2. _How?_ — **both engines**: SQLite runs everything now, PostgreSQL stays for
   the future, and SQLite gets the equivalent migrations.

So the goal is not "replace PostgreSQL". It is "stop needing a server to run
this project, without giving up the guarantees PostgreSQL was chosen for, and
without throwing away the PostgreSQL work".

## Decision

### 1. Two persistence stacks, one set of ports

`packages/domain` already declares every repository as a port
(`AppointmentRepository`, `PatientRepository`, `VisitRepository`,
`ClinicRepository`, `DentistRepository`, `ChairRepository`, `UnitOfWork`). The
domain never learns which implementation it was handed — that was ADR 0014's
seam and ADR 0003's "the repository port already gives the extension point".

- **`persistence/sqlite/` is the default and runs everything.**
- **`persistence/postgres/` is kept as-is.** It still compiles, it still has its
  integration suite, and it is still the intended engine for a multi-clinic or
  server deployment.
- The engine is chosen by configuration, never by an `if` inside a use case.

### 2. The schema is declared twice, on purpose

Drizzle's `pgTable` and `sqliteTable` are different APIs over different type
systems, so `database/schema` (PostgreSQL) and `database/schema/sqlite` both
exist, table for table, file for file, in the same bounded-area layout.

A single declaration driving both was considered and rejected — see
"Alternatives rejected". The two files are kept honest by the same argument
that keeps the domain and `DATABASE_ENUM_VALUES` honest: a table added to one
and not the other fails the build when a repository that needs it is compiled
against the wrong one, and `docs/database.md` lists both trees.

### 3. Every PostgreSQL-only guarantee has an explicit SQLite equivalent

This is the part that decides whether the switch is honest. Each of these is
enforced **by the database** in both engines, or the ADR says so in as many
words:

| PostgreSQL                                                  | SQLite equivalent                                                                                 |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `EXCLUDE USING gist` on appointments (3 constraints)        | `BEFORE INSERT` / `BEFORE UPDATE` triggers with `RAISE(ABORT, …)`                                 |
| IMMUTABLE `appointment_ends_at()`                           | inline arithmetic — never a stored column (ADR 0012)                                              |
| `ON DELETE SET NULL (dentist_id)` on a composite tenant key | `BEFORE DELETE` triggers on `dentists` / `chairs` / `rooms` that null only the referencing column |
| Composite tenant foreign keys over `(id, clinic_id)`        | unchanged — SQLite supports composite keys                                                        |
| `timestamptz`                                               | `INTEGER` epoch milliseconds, UTC                                                                 |
| `enum` types                                                | `TEXT` with Drizzle's `{ enum: […] }` + `CHECK`                                                   |
| `text[]` / `enum[]`                                         | `TEXT` holding JSON                                                                               |
| `numeric(p,s)`                                              | `REAL` (only quantities and tax rates; money is already integer minor units)                      |
| `gen_random_uuid()`                                         | generated by the application's `IdGenerator` — the domain already allocates every id              |
| `pg_advisory_xact_lock`                                     | not needed: `better-sqlite3` is one synchronous connection and SQLite serialises writers          |
| `record_number ~ '^P-[0-9]+$'`                              | the same predicate, evaluated in TypeScript                                                       |
| `to_char(… at time zone 'UTC', 'YYYY-MM-DD')`               | `strftime('%Y-%m-%d', starts_at / 1000, 'unixepoch')`                                             |

The overlap trigger is the load-bearing one. SQLite has no exclusion
constraints, so the rule "a dentist cannot be in two places at once" is
enforced by a trigger that compares integer milliseconds with the same
half-open `[from, to)` arithmetic the domain uses
(`packages/domain/appointment`) and the same partial-index predicate
PostgreSQL uses (`status not in ('CANCELLED', 'NO_SHOW')`). A trigger is not a
weaker form of the guarantee here: SQLite has a single writer, so the check and
the insert happen inside one lock, where PostgreSQL needed the GiST index to
make the check atomic across connections.

### 4. The engines are selected by `DATABASE_URL`, not by a flag

- `sqlite:./data/denti.db` or `file:./data/denti.db` → SQLite (the default)
- `postgres://…` → PostgreSQL

One variable, no second switch to forget, and `.env.example` can show both.

### 5. The test strategy keeps PostgreSQL honest

- `pnpm run test:integration` runs against **SQLite** — no container, no
  `global-setup` database creation, runs in CI and on a fresh clone.
- `pnpm run test:integration:postgres` runs the same suite against **real
  PostgreSQL**, because a suite that only ever ran on SQLite would not notice
  the day the PostgreSQL stack is needed again. It is the opt-in run that
  requires Docker.

## Rationale

- **The container was the problem, not the engine.** SQLite removes it while
  leaving every guarantee in place; PGlite or a native PostgreSQL install would
  have removed it too, but both still make a contributor install or download a
  database engine, and the product owner asked for SQLite specifically.
- **The ports already exist.** ADR 0003's own diagram predicted this:

  ```
  Application → RepositoryInterface → { ServerRepository → PostgreSQL
                                      { LocalRepository  → SQLite
  ```

  We are filling in the second line. Nothing in the domain changes, which is
  the point of having paid for the seam.

- **Money is already integer minor units** and all write paths supply their own
  ids, so the two places SQLite is genuinely weaker than PostgreSQL — numeric
  precision and server-generated keys — were already designed around.

## Consequences

Positive:

- `pnpm install && pnpm dev:api` starts a working API with no container, no
  port, no volume, no migration server.
- The database becomes a file: copy it, back it up, put it in `.gitignore`.
- The PostgreSQL stack is retained rather than rewritten, so a future
  multi-clinic deployment does not start from zero.

Negative / accepted costs:

- **Every new repository method is written twice.** This is the standing cost
  of the decision and it is recorded here so nobody rediscovers it as a
  surprise. If it becomes the bottleneck, the answer is to drop one engine, not
  to invent an abstraction over both.
- **The two schema trees must move together.** A column added to only one is a
  defect that surfaces at the first compile error against the other.
- **The concurrent-write race test cannot be expressed on SQLite.** It stays in
  the PostgreSQL suite, where two connections can genuinely collide. The SQLite
  suite proves the overlap trigger refuses a second overlapping write; it
  cannot prove what happens when two sockets arrive at once.
- **`better-sqlite3` is a native module.** It needs a prebuilt binary or a
  local build, which is a smaller dependency than a container but is not zero.

## Alternatives rejected

- **PGlite (PostgreSQL compiled to WASM, no Docker):** the technically closest
  answer — `btree_gist` is bundled, so the exclusion constraints would have
  survived unchanged. Rejected because the product owner asked for SQLite, and
  because a single-connection WASM build still leaves the concurrency suite
  unrunnable while adding a WASM runtime to the server.
- **Native PostgreSQL, drop Docker only:** zero code change and every guarantee
  intact, but every machine still has to install and manage a database server.
  It removes the container without removing the dependency.
- **One schema and one set of repositories abstracted over both engines:**
  rejected by ADR 0003 and by rule 18, and rejected again here. Drizzle cannot
  type a `pgTable` and a `sqliteTable` through one signature without degrading
  to `any`, and a schema that accepts `any` has traded a compile error for a
  wrong query at runtime — which is exactly the failure this codebase's
  projection comments exist to prevent.
- **SQLite only, delete the PostgreSQL stack:** rejected by the product owner's
  "keep the implementation of postgres for future".

## Verification

- `pnpm run guard:boundaries` fails if anything outside `apps/api` and
  `database/` imports `drizzle-orm`, `better-sqlite3` or `postgres`, or if
  `packages/domain` imports any infrastructure.
- `pnpm run test:integration` proves the SQLite triggers refuse an overlapping
  booking, the tenant keys refuse another clinic's patient, and the walk-in and
  visit flows write both rows or neither.
- `pnpm run test:integration:postgres` proves the PostgreSQL stack still does
  the same, so keeping it is a claim with evidence behind it.
- `docs/database.md` documents both schema trees and both migration chains.
